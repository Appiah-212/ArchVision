# ArchVision AI Phase 2 architecture

## Scope and evidence

This document describes the repository implementation reviewed for Phase 2.7. Puter identity injection, KV consistency, storage ACLs, hosted asset revocation, and AI service retention are external service behavior and were not independently verified. No cloud service was changed and no live AI request was made.

## Runtime and trust boundaries

The application is React 19 and TypeScript using React Router SSR, Vite, and Tailwind. The browser uses the Puter SDK for sign-in, Worker calls, user-scoped KV/filesystem access, and explicit AI calls. `VITE_PUTER_WORKER_URL` selects the Worker endpoint. Worker routes are implemented in `lib/puter.worker.js`.

```text
Browser UI and local validation
  ├─ Puter sign-in and authenticated Worker request
  │    └─ Worker checks injected user context and auth.getUser().uuid
  │         ├─ caller-scoped KV: private project/workspace records
  │         ├─ shared KV: public copies, quota counters, generation locks
  │         └─ filesystem: owner-scoped private assets and hosted public copies
  └─ explicit AI action through Puter SDK
       ├─ floor-plan interpretation → schema validation → review/approval
       └─ authorized image generation → private asset upload → version commit
```

The browser is untrusted. Important record shapes, ownership, quota, generation authorization, project/version/evaluation associations, and private asset references are validated again by the Worker. AI image generation runs in the browser through Puter after Worker authorization. The Worker does not verify provider-signed output provenance; a project owner who controls the browser can submit a different image under an authorized context. Research provenance is application-recorded, not tamper-proof attestation.

## Data flow

1. **Authentication and upload.** `components/Upload.tsx` and `lib/file-validation.ts` validate type and size locally. `lib/puter.action.ts` stores source bytes through the private-asset route, then saves the project record. The Worker accepts PNG/JPEG/WebP/GIF up to 50 MiB and now checks the matching leading image signature. Asset storage and project metadata save are separate calls; failure can leave an orphan file.
2. **Project retrieval.** Owner-scoped private projects are loaded from caller KV. Private images are served after checking authenticated owner and the project’s stored reference. The UI resolves images into browser object URLs; project list loading may fetch source, active render, and all version images. Public projects are read from shared KV and hosted assets.
3. **Analysis and approval.** `lib/ai.action.ts` requests analysis through Puter AI. `lib/floor-plan-analysis.ts` validates the structured result. The owner reviews/corrects it in `FloorPlanAnalysisPanel`; Worker save persists the approved analysis and increments its revision. Analysis is omitted from public serialization.
4. **Design settings.** `lib/render-configuration.ts` defines the client schema; the Worker validates it independently and stores it on the private project. Enhanced generation requires saved settings and approved analysis.
5. **Generation and versions.** `lib/generation-workflow.ts` and `lib/ai.action.ts` obtain authorization before calling Puter image generation. Analysis and render generation share one daily quota. Worker authorization reserves a project lock and assigns version ID/number. The browser uploads the generated bytes and commits the version; previous successful renders remain in history. Active-version selection and name/notes use separate owner-only routes.
6. **Fidelity review.** `StructuralFidelityPanel` creates six-criterion human assessments from a selected render snapshot. The Worker verifies owner, source reference, version provenance, rubric/schema, and immutable record ID. Revisions are new linked records.
7. **Research.** `Research` loads the owner workspace and validated project summaries. Dataset registration references an owned source. Each pair references baseline and enhanced renders from that same registered project and optional exact-version assessments. Comparisons append; stored reviews cannot be silently replaced. `lib/research-evaluation.ts` computes descriptive metrics.
8. **Export and sharing.** Research exports pseudonymize project linkage and omit image URLs/bytes and direct owner identifiers. Fidelity downloads now omit project/reviewer identifiers and private source/settings/analysis details. Sharing uploads the source and selected active render to hosted paths and writes a sanitized public record. Unsharing removes the public record and hosted assets; live revocation behavior still needs validation.

## Persistence and deployment

Private projects use `archvision_project_<owner UUID>_<project ID>` in the authenticated user KV, with legacy-key fallback. The research workspace uses `archvision_research_workspace_<owner UUID>`. Private files are under `archvision_private_assets/<owner UUID>/<UUID>.<extension>` and project records retain opaque `archvision_private_asset:` references. Public copies use shared key `archvision_public_project_<project ID>` and hosted paths below `projects/<encoded project ID>/`.

Puter KV/filesystem operations are separate calls. The implementation uses read/validate/write sequences without transactions or compare-and-swap. Concurrent updates can race; interruption between calls can leave incomplete metadata or orphan files. Partial render upload cleanup exists, but source upload/project save and public asset/KV changes are not atomic.

The only client environment variable found in application source is `VITE_PUTER_WORKER_URL`, a public endpoint rather than a secret. `react-router.config.ts` enables SSR. The Dockerfile targets Node 24 Alpine and runs `react-router-serve`; Docker was not run for this review. The app creates conceptual renders, not verified CAD/BIM geometry. Human visual scores do not establish geometric accuracy, code compliance, or professional suitability.
